## Part B — NEW BUGS found in this audit (F-series)

### F1. HIGH — Fallback sharpness range is off by ~3 orders of magnitude; every pre-calibration swing is a Home Run
`scoring.py::FALLBACK_SHARPNESS_LOW_HIGH = (150.0, 600.0)`, used whenever
the reference has <3 values (i.e. every fresh install until first
calibration). Real hardware sharpness values from `swings.csv` replay
(peak/rise): **65,611 to 1,435,070**. Every conceivable real swing lands
above 600 → bucketed "High" → any Perfect/Great timing = Home Run, and
"Good" = Line Drive. The entire sharpness axis is a no-op before first
calibration, which is exactly the state every playtester starts in.
**Fix:** re-derive the fallback range from the real capture (e.g. roughly
60k–250k given the observed spread), and make it a constant documented as
hardware-derived, not a placeholder.

### F2. HIGH — Sharpness metric is in the quantization regime the build plan warned about; derivative variant is dead code; `rise_duration == 0` scores the sharpest swing as the weakest
Three related problems in one metric:

1. Measured device rate is ~66Hz (<100Hz), the exact regime where the plan
   mandates the max-derivative variant. `scoring.raw_sharpness()` has the
   `max_derivative` parameter, but **nothing ever computes or passes it** —
   `IctusEvent` has no such field and `ictus_detector.py` never measures it.
   Dead code masquerading as spec compliance.
2. Quantization confirmed in real data: captured rises include 15.0ms and
   30.1ms (1 vs 2 samples) with similar peaks, producing sharpness values
   ~10× apart (1,435,070 vs 834,524, vs a 90ms swing at 237,115).
   Percentile bucketing on values this quantization-distorted is unstable.
3. Edge case: `rise_duration = peak_t - rise_start_t` is 0.0 when the peak
   is the first RISING sample (violent swing peaking within one ~15ms
   interval — plausible at 66Hz). `raw_sharpness` then returns 0.0 → "Low"
   bucket → **the sharpest physically possible swing scores as a Bunt.**

**Fix (one change covers all three):** track max per-sample positive
smoothed-magnitude delta during RISING, add it to `IctusEvent`, and pass it
to `raw_sharpness` everywhere (detector → `game.py::_judge`, and the
settings_menu seed computation). Remove the peak/rise_duration path or keep
it only as a fallback with a `rise_duration > 0` guard.

### F3. HIGH — Three inconsistent sampling regimes make thresholds and the calibration seed non-transferable (root cause underlying A5)
The same `IctusDetector` constants are applied to three different effective
sample rates:

- `joycon_stream.py::main()` (Phase 0 capture): unthrottled, ~25,000
  samples/s, ~375 duplicate reads per real update.
- `game.py::run_game()`: `clock.tick(200)` → ~200Hz, ~3 duplicates per
  real update.
- `settings_menu.py::run_calibration()`: `clock.tick(60)` → ~60Hz,
  **below** the device's ~66Hz rate, so real updates are dropped.

`RISE_RATE_THRESHOLD` (50.0) and `SMOOTHING_WINDOW` (4) are **per-sample**
quantities — their physical meaning changes with poll rate. Consequences:
thresholds tuned on Phase 0 CSVs don't describe gameplay; sharpness values
recorded during calibration (60Hz regime) seed a distribution that live
gameplay (200Hz regime) is then bucketed against — statistically not the
same measurement. Fixing A5 by throttling `stream()` alone leaves the
60-vs-200 calibration/gameplay mismatch in place.
**Fix:** pick ONE poll rate (matched to the device, e.g.
`poll_interval_s≈0.005` plus a consecutive-duplicate skip in `stream()`),
use it in all three call sites, and re-express rise-rate as units/second so
it survives future rate changes. Do this before any Phase 4 tuning
(rev. 1's ordering stands).

### F4. MEDIUM — `pygame.time.wait(600)` after each judgment blocks the sample loop through beat 2; wind-up ictuses are systematically lost
`game.py::run_game()`: after a record, `_draw_popup` +
`pygame.time.wait(600)` freezes the generator loop. The window closes at
~beat1+375ms; the popup holds until ~beat1+975ms; the beat-2 rebound lands
at beat1+750ms — **inside the frozen span, every single measure.** So:
(a) the wind-up consistency stat the summary screen advertises will be
empty or near-empty in real play (its data source is structurally
suppressed); (b) the detector sees a ~600ms gap each measure and its
time-based states (REFRACTORY, RISING timeout, min-seek timeout) resolve
against stale sample timestamps; (c) QUIT events are ignored during the
wait.
**Fix:** replace the blocking wait with a "popup visible until
`t_popup_end`" flag inside the normal sampling loop.

### F5. MEDIUM — A failed calibration silently clobbers a previous good calibration
`calibration.compute_offset()` with zero valid candidates returns the
*loaded* offset (`from_default=True`) — but
`settings_menu.run_calibration()` ignores `from_default` and
unconditionally calls `save_calibration(result.offset_s, sharpness_seed)`.
If the player stands still (or detection fails) during calibration: the
offset is rewritten harmlessly, but the previously saved, hard-earned
`sharpness_seed` is **overwritten with an empty list or pure noise
events**. Next launch falls back to the broken F1 range.
**Fix:** when `from_default` is true (or fewer than ~3 matched swings),
leave the existing file untouched and tell the player calibration didn't
take.

### F6. MEDIUM — Sharpness seed includes unmatched/noise ictuses, not the calibration swings
`run_calibration()` computes `sharpness_seed` from **all**
`detected_ictuses`, while the offset correctly uses only the per-measure
closest-match events. Rebound gestures, duplicate-reading artifacts (A5:
+50% spurious events in the current stream), and idle noise all enter the
reference distribution that live swings are percentile-bucketed against —
skewing it low and inflating live bucket ranks. The build plan (4c)
specifies seeding from *the calibration swings*.
**Fix:** seed only from the events selected into `closest_per_measure`
(keep their peak/rise or max-derivative fields alongside the timestamp when
matching).

### F7. LOW — EXPECTING_ICTUS window is not shifted by the calibration offset
`MeasureJudge` windows are `beat1 ± half_beat` in **raw** time, but tiers
judge `raw − offset`. With the 50ms default offset the effective corrected
window is asymmetric (−425ms/+325ms); a larger measured offset worsens it.
Cosmetic at current magnitudes; center the window at `beat1 + offset` when
convenient.

### F8. LOW — `run_calibration()` return-value inconsistencies (latent trap)
Declared `-> None` but returns `sharpness_seed` on success and bare
`return` on the hardware-failure and QUIT paths; the caller ignores it, and
the in-memory `SharpnessReference`/offset in any *future* "play again" flow
would be stale (the current exit-after-settings flow masks this). Also the
QUIT-during-calibration path stops the metronome and saves nothing —
correct, but worth a comment so F5's fix doesn't "helpfully" add a save
there.

### F9. LOW — Setup/doc gaps (carried from rev. 1, still open)
(a) `joycon_stream.py` catches all `ImportError`s with one message that
misdiagnoses the two known Windows issues — print the underlying exception
text. (b) Add `hidapi` (not `hid`) and `PyGLM` to the install notes in
`Swinger_Build_Plan_v1.md` Phase 0. (c) `calibration.json` is written to
the project root — confirm it's in `.gitignore` (plan says runtime-only).

### F10. LOW / informational — Smoothing lag shifts ictus timestamps by ~2 samples
The 4-sample moving average delays the detected local minimum by roughly
(window−1)/2 samples (~23ms at 66Hz). Constant-ish, so calibration absorbs
it — **but only while the sample rate is constant**, which is another
reason F3 must land before Phase 4 tuning. Also note `game.py` draws no
batter/ball placeholder (plan 4d asks for them) — a scope gap, not a bug.
