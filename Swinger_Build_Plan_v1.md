# Build Plan v1 — All-Star Swingers (Conducting Rhythm Baseball Minigame)

## 0. Context (read this first)

This is the first playable skeleton for **All-Star Swingers**, one minigame in
a Mario-Party-style set that doubles as a conducting-technique trainer. The
long-term project is a VR chord game in Unity, plus a separate Joy-Con-based
conducting analysis tool. This minigame is the first place those two threads
meet: instead of scoring "did you press a button on time," we score "did you
produce a clean conducting ictus (the direction-change point at the bottom of
a downbeat) at the right time."

Background the implementer needs:

- **Time signature**: 2/4 only, for this v1. Beat 1 = downbeat = the ictus we
  detect and score. Beat 2 (the rebound/up-stroke) is not scored in this version.
- **Input device**: Nintendo Switch Joy-Con — **right Joy-Con only** for this
  version (single controller, not a paired set). Connected over Bluetooth,
  read via the `joycon-python` / `hid` Python library. No soldering, no
  custom hardware.
- **Sensor signal**: raw combined gyroscope magnitude (`sqrt(gx^2 + gy^2 + gz^2)`
  or equivalent vector norm depending on library output units). We are
  explicitly NOT doing per-axis calibration or dominant-axis detection in v1 —
  that's a deferred improvement (see Section 6). Raw magnitude only.
- **No song yet.** The pitch/tempo source is a metronome click generated by
  the program itself (fixed BPM), not audio analysis of a real piece. This
  removes audio-sync complexity from this phase. Note the direction of this
  relationship is temporary — see the "future direction" bullet below.
- **Beat detection target**: not the peak of gyro magnitude, but the point
  right after the peak where velocity sharply drops back toward zero — i.e.
  the direction-change / deceleration event. This is the "ictus." See Section
  3 for the concrete detection algorithm.
- **Calibration**: never runs automatically. On startup the game only
  **loads** a previously saved offset from disk (if present); running
  calibration itself is a **Settings-menu action, offered after a round
  ends** — not a mandatory pre-round step. The measured latency offset
  **persists across sessions** (saved to disk) until the player re-runs
  calibration. A fresh install with no saved offset falls back to a
  **shipped default offset** measured once on the dev machine (see 4a) —
  not 0, because Bluetooth + audio-output latency makes `offset = 0`
  unplayable at the Perfect/Great window sizes. See Section 4a.
- **Game**: baseball batting. A "pitch" arrives once per measure on beat 1.
  Player swings once per measure. Contact quality depends on timing accuracy
  (hit tier) and gesture sharpness (how clean the direction-change is). 3
  misses = out (classic tension structure), matching typical minigame length
  in the Mario Party set this is modeled on.
- **Future direction (do not build yet, but design should not paint us into a
  corner):** the current model is "audio leads, conductor follows" — the
  metronome sets the tempo and the player's swing is judged against it. A
  later version inverts this: the **conductor leads, audio follows** — i.e.
  the game's tempo should dynamically track the player's own conducting pace,
  the way a real ensemble follows a conductor rather than a conductor
  following a click track. This has real implications for the detector and
  scoring code (Section 3–4), so keep detection and "expected beat time"
  logic in clearly separable functions rather than hard-wiring "beat source
  = fixed metronome schedule" throughout. Full detail is out of scope for
  v1; just don't make this refactor harder than it needs to be.

**Platform roadmap (clarifies the earlier "Python pygame" assumption):**
this project has three stages, and v1 covers only the first:

1. **v1 (this document): Python rule-based prototype.** Standalone script
   using `pygame` for the game loop/visuals/audio and `joycon-python`/`hid`
   for sensor input. Visuals are flat 2D placeholders (shapes/sprites, no 3D
   rendering) — the goal is validating detection, calibration, and scoring
   logic, not final look.
2. **Next stage (not this document): 2.5D in Unity.** Presentation moves to
   Unity with 3D character models on a fixed camera/stage — the player does
   not move around the space, matching how Super Mario Party minigames work
   (3D characters and environment, but no free player movement/navigation).
   The detection/calibration/scoring logic from v1 ports into C# largely
   as-is; only the input/rendering layer changes.
3. **Long-term: VR**, converging with the existing VR chord-game project and
   sharing its technical base.

Keep this roadmap in mind but do not build Unity or VR scaffolding now —
v1's job is to prove the rule-based detection works and feels right, cheaply,
in Python.

**Definition of "v0 prototype-ready":** by the end of Phase 3 below, a single
person with a paired right Joy-Con must be able to run one command, hear a
metronome, swing the Joy-Con once per measure, and see: a beat-timing
judgment (Perfect/Great/Good/Miss), a sharpness-based hit quality
(bunt/line drive/home run), an out count, and an end-of-round summary of
timing offsets and sharpness — with a Settings option to run/re-run
calibration after the round. All of Sections 1–5 must be functional, not
stubbed.

## 1. Phase 0 — Environment & Raw Signal Verification

**Goal:** prove we can reliably read right-Joy-Con gyro data before writing
any game logic on top of it.

- Set up Python env, install `joycon-python`, `pygame`. On Windows,
  `joycon-python` needs `hidapi` (not the `hid` PyPI package, which is a
  different, incompatible library) and `PyGLM` — `pip install joycon-python
  hidapi PyGLM`. If `import pyjoycon` still fails, check the printed
  underlying exception (`joycon_stream.py` surfaces it) before assuming the
  device/pairing is at fault.
- Pair one **right** Joy-Con over Bluetooth; write a minimal script that
  streams gyro x/y/z at the library's native rate (expect roughly 60–200Hz
  depending on driver) and prints raw values to console.
- **Timestamp every sample with `time.perf_counter` at host read time.**
  All later phases compare sensor timestamps against expected beat
  timestamps, which are also `perf_counter`-based (Phase 1) — everything
  must live in this one clock domain. Do not use any timestamps the library
  itself provides; they are a different clock.
- **Log and report the actual achieved sample rate** (mean interval and
  jitter). Phase 2's sharpness metric depends on it: below ~100Hz,
  rise-duration quantization gets large and the sharpness formula must
  switch to its derivative-based variant (see 4c).
- Compute and print combined magnitude per sample:
  `mag = sqrt(gx**2 + gy**2 + gz**2)`
- Log a few seconds of a person doing a deliberate down-swing motion to a CSV
  file, sanity-check that magnitude visibly spikes and the log has no dropped
  samples/large gaps.
- **Exit criterion:** a CSV of at least 10 clean swing gestures, with visible
  magnitude peaks, no missing timestamps. Record swings at three deliberate
  intensities (soft / medium / hard) — Phase 2's validation needs this
  spread to check for amplitude-dependent timing bias.

**Risk note — this is the highest-risk phase; timebox it.** `joycon-python`
is thinly maintained and Windows Bluetooth HID pairing is known to be flaky.
If the library can't produce a stable stream within the timebox, fall back
in this order rather than debugging indefinitely: (1) the `pyjoycon` fork /
alternate hidapi backends, (2) a BetterJoy-style driver bridging the Joy-Con
to a virtual controller read via `pygame` joystick APIs. A driver problem
here is a "stop and flag" event per Section 6, not something to absorb
silently.

Deliverable file: `joycon_stream.py` (standalone read/log utility, reusable
in later phases).

## 2. Phase 1 — Metronome & Game Clock

**Goal:** a stable, self-contained timing reference. No sensor logic yet.

- Fixed BPM (constant/config value, default 80 BPM). **Convention, fixed
  here to remove ambiguity: BPM counts beats, not measures.** At 80 BPM in
  2/4, beats are `60/80 = 0.75s` apart and beat 1 arrives every `1.5s`.
  **Click on every beat** (players need the beat-2 click to time their
  wind-up), but only beat 1 is scored. Distinguish the beat-1 click audibly
  (higher pitch or accent) so the downbeat is unambiguous by ear.
- Use `pygame.mixer` to play the click sounds. **Call
  `pygame.mixer.pre_init(frequency=44100, buffer=256)` before
  `pygame.init()`** — the default mixer buffer adds easily 60–150ms of
  output latency, which would silently eat the entire Perfect window. Use a
  high-resolution clock (`time.perf_counter`) for scheduling, not `pygame`
  frame timing, to avoid drift; on Windows, plain `time.sleep` has ~15ms
  granularity, so schedule with a coarse-sleep-then-short-spin pattern in a
  dedicated thread.
- Maintain a running list of "expected beat timestamps" for the session,
  generated at session start (not computed live), so later phases can just
  look up "what was the expected time for beat N." Write this as its own
  function/module (e.g. `beat_schedule.py`) rather than inlining it in the
  metronome — the future "conductor leads" direction (Section 0) will need
  to swap this out for a schedule derived from the player's own tempo, so
  keep "what time is beat N expected" cleanly separated from "play a click."
- Visual metronome: simple pulsing shape or beat counter on screen in sync
  with the audio click, for players who prefer a visual cue.
- **Exit criterion:** clicks stay in time over a 2+ minute run with no
  audible drift (verify by logging the timestamps at which `play()` was
  called vs. expected, and checking the delta stays flat, not growing).
  Note this measures scheduling drift only — it cannot see the constant
  speaker-output latency, which is invisible to software and is exactly
  what calibration (4a) exists to absorb.

Deliverable: `metronome.py`, `beat_schedule.py`.

## 3. Phase 2 — Ictus (Beat) Detection

**Goal:** turn the raw gyro stream into discrete, timestamped "ictus events."

**Algorithm (raw magnitude, beat 1 only):**

1. Compute `mag[t]` per sample as in Phase 0.
2. Apply light smoothing: simple moving average over 3–5 samples. Keep this
   window small — the goal is killing single-sample jitter, not flattening
   the direction-change spike.
3. Track a rolling state machine per candidate gesture:
   - **Armed**: waiting for a fast rise. Enter "rising" state when
     `mag[t] - mag[t-1]` exceeds a rise-rate threshold (tune empirically from
     Phase 0 logs).
   - **Peak tracking**: while rising, track the running max magnitude.
   - **Ictus candidate**: once magnitude has risen past a minimum peak
     threshold (filters out small hand jitter from counting as a swing) and
     then drops sharply — i.e. `mag[t]` falls below some fraction (e.g. 60%)
     of the tracked peak within a short time window (e.g. 80ms) — the swing
     qualifies. For the **ictus timestamp**, prefer the **post-peak local
     minimum of magnitude** (the actual direction-change / velocity
     zero-crossing) over "first sample of the sharp drop." The 60%-of-peak
     crossing point shifts with swing intensity (a hard swing crosses 60% of
     a tall peak at a different point in the gesture than a soft swing),
     which would couple the timing score to swing strength and make a
     calibration done at one intensity not transfer. Use the drop-fraction
     test only as the *qualifier* that a real ictus happened; use the local
     minimum as the *timestamp*.
   - Reset to Armed after an ictus is recorded, with a short refractory
     period (e.g. 150–200ms) to prevent double-counting noise around the
     same swing.
4. All three thresholds (rise-rate, peak minimum, drop fraction/window) are
   named constants in a config block at the top of the file — expect to tune
   these against Phase 0's recorded CSVs before trusting live detection.
5. Emit each detected ictus as `(timestamp, peak_magnitude, rise_duration)` —
   these three fields are exactly what Phase 4's sharpness score needs, so
   don't discard them after detection.

**Validation step (required before moving to Phase 3):** replay the Phase 0
CSVs through this detection function offline and manually verify each real
swing produces exactly one ictus event, with no missed swings and no false
positives from hand tremor/idle movement. Print a simple before/after plot
(magnitude trace with detected ictus points marked) — this can be a
throwaway matplotlib script, doesn't need to ship in the final game.
Additionally, using the soft/medium/hard swings from Phase 0, **plot
detected-timestamp position vs. peak magnitude and confirm it's flat** — if
the detected ictus time systematically shifts with swing intensity, the
timestamp rule above needs fixing *before* Phase 3 builds scoring on top of
it.

Deliverable: `ictus_detector.py`, plus the validation script and its output
plots saved for reference (not required to be pretty, just needs to show
detection is working before Phase 3 depends on it).

## 4. Phase 3 — Calibration, Scoring, and the Batting Game Loop

This is the phase where "prototype-ready" happens — everything below must be
wired together and playable.

### 4a. Calibration (persistent, accessed via Settings after a round)

- Calibration is **not** run automatically at the start of every session.
  Flow is: player launches the game → plays a round using whatever offset is
  currently saved → round ends → on the post-round screen, a **Settings**
  option is available, and **Calibrate** lives there.
- **First-ever run (no saved file):** do NOT default to `offset = 0`. The
  chain of Bluetooth HID latency (~15ms packets) plus audio output latency
  makes a zero offset likely to put even a metronome-perfect player outside
  the 50ms Perfect window before they've ever seen the Calibrate option —
  failing the Phase 4 "first-time player" exit criterion. Instead, ship a
  `DEFAULT_OFFSET` constant measured once on the dev machine during Phase 3
  and use it until the player calibrates. If that still proves unreliable
  across machines, widen the timing windows (4b) whenever the player is on
  the shipped default, and restore the tight windows after first
  calibration.
- When the player chooses Calibrate: run the metronome (Phase 1) for N
  practice measures — **use 8–12, not 4**: the same swings also seed the
  sharpness reference distribution (4c), and percentile bucketing against
  only 4 data points is noise.
- For each practice measure, find the ictus event (Phase 2) closest to that
  measure's expected beat-1 timestamp.
- Compute `offset = mean(ictus_timestamp - expected_timestamp)` across the
  practice measures. Discard outliers (e.g. a missed swing that grabs a
  wrong-measure ictus) with a simple sanity bound before averaging — e.g.
  ignore any candidate offset larger than half a beat.
- **Persist** the resulting `offset` to a small local file (e.g.
  `calibration.json`) so it survives across app restarts, not just within
  the current process. Load it on startup if present.
- All timing judgments (4b) compare `(ictus_timestamp - offset)` against the
  expected beat timestamp, using whatever offset is currently loaded —
  freshly recalibrated or carried over from a previous session.
- **Known design decision, accepted for v1:** this offset absorbs the
  player's habitual earliness/lateness along with system latency — the two
  are indistinguishable from a single-device measurement. For the game
  that's fine; for the conducting-trainer angle it erases a tendency worth
  seeing. Mitigation: the post-round summary (4d) must show **raw,
  uncorrected offsets** alongside the judged tiers, so consistent bias
  stays visible even after calibration nulls it from scoring.
- **Exit criterion:** after calibrating once, closing and relaunching the
  game, a player swinging consistently on-beat should still land in the
  "Perfect" tier most of the time without recalibrating — proving the offset
  actually persisted and loaded correctly.

### 4b. Timing judgment

Compare corrected ictus timestamp to the expected beat-1 timestamp for that
measure. Tiers (tune after playtesting, these are starting points):

- Perfect: within 50ms
- Great: within 100ms
- Good: within 150ms
- Miss: beyond 150ms (but still inside the EXPECTING_ICTUS window — see
  4d), or no ictus detected at all inside that window

The tier boundaries live *inside* the EXPECTING_ICTUS window (4d), which is
strictly wider than 150ms; keep the 150ms constant and the window-bounds
constant explicitly separate in code so tuning one never silently changes
the other.

### 4c. Sharpness score

Using the `(peak_magnitude, rise_duration)` captured at detection time:

- Define raw sharpness as something like `peak_magnitude / rise_duration`
  (steeper, higher-magnitude spikes score higher). **Caveat from Phase 0's
  measured sample rate:** below ~100Hz, `rise_duration` spans only a
  handful of samples and ±1 sample of quantization is a large relative
  error in the denominator. In that case use the **maximum per-sample
  positive derivative of magnitude during the rise** as the raw sharpness
  value instead — same intent (how violently the gesture accelerates), far
  less quantization-sensitive.
- **Bucket per-player, not against a fixed global constant.** Gyro magnitude
  scale varies with arm length and individual swing habit, so a fixed
  threshold penalizes players with naturally smaller swings even when their
  gesture is clean. Instead, use the raw sharpness values recorded during
  that player's own calibration swings (Section 4a) as the reference
  distribution, and bucket live swings by percentile against it (e.g.
  bottom third / middle third / top third of the calibration-swing
  distribution). If calibration hasn't been run yet (fresh install on the
  shipped default offset), fall back to a hardcoded reasonable range from
  Phase 0/2 testing until the player calibrates at least once. To keep the
  reference from going stale (or from resting on only 8–12 swings), also
  fold the player's own recent gameplay swings into the reference as a
  rolling window — calibration seeds the distribution; play refines it.
- Map the resulting bucket into 3 hit-quality tiers for the game: **Bunt**
  (low), **Line Drive** (mid), **Home Run** (high). This is independent of
  the timing tier — a swing can be a well-timed but weak Bunt, or a
  mistimed Good/Home-Run combo. Both dimensions display in the summary.

### 4d. Batting game loop

**Per-measure state machine.** Each measure carries two beats, but only beat 1
is scored; beat 2 (the previous measure's rebound/up-stroke) is the wind-up
and is logged for consistency data only, never scored or counted toward
misses (see Section 6 — beat 2 scoring is deferred). Model each measure as:

1. **WINDUP** — spans beat 2 of the previous measure through just before the
   current beat 1. Any ictus detected here is recorded (for the
   inter-beat-interval consistency stat) but does not affect score or outs.
2. **EXPECTING_ICTUS** — a window around the current measure's expected
   beat-1 timestamp during which the detector (Phase 2) is actively looked to
   for a qualifying ictus. **Window bounds, explicit: expected beat-1
   timestamp ± half a beat** (±375ms at 80 BPM) — a named constant, wider
   than the 150ms Miss boundary by design so that a clearly-attempted but
   badly early/late swing (e.g. −200ms) is classified as a *late/early Miss
   with a measurable offset* rather than silently falling into WINDUP and
   becoming an indistinguishable "no swing" Miss. Everything inside the
   window gets a timing classification per 4b; everything outside it is
   WINDUP material. Once an ictus fires inside the window, lock it in
   immediately and stop looking until the next measure's window opens — do
   not let a second ictus in the same window overwrite the first.
3. **JUDGE** — resolve the locked-in ictus (or its absence) into a result per
   the tier lookup below, update score/outs, show the popup, then advance to
   the next measure's WINDUP.

If beat 1's window closes with no qualifying ictus locked in, that measure is
an automatic Miss — this is a **timing** miss specifically. A swing that
lands on time but with minimal sharpness (a "checked swing") is still a
timing hit — it resolves to Bunt via the tier lookup below, not a miss.
Sharpness never causes a miss or contributes to the out count in v1; it only
affects hit quality. Keep this distinction explicit in the scoring code
rather than folding sharpness into a single combined miss condition, since
it's an easy place to accidentally conflate the two dimensions later.

**Timing × sharpness → outcome.** Resolve the contact result as a small
lookup table (timing tier down the rows, sharpness bucket across the
columns) rather than a formula — this is easier to tune by feel during
playtesting (Phase 4) than reverse-engineering coefficients, and gives a
natural place to log which cell gets hit most often for balancing later.
Starting point (tune freely):

| Timing \ Sharpness | Low        | Mid         | High      |
|--------------------|------------|-------------|-----------|
| Perfect            | Bunt       | Line Drive  | Home Run  |
| Great               | Bunt       | Line Drive  | Home Run  |
| Good                | Bunt       | Bunt        | Line Drive|
| Miss                | Miss (strike/out) — sharpness irrelevant |

- Simple visuals are enough for v1: batter sprite/rectangle, ball, a
  text/score popup per swing (e.g. "PERFECT — Home Run!"). This is flat 2D
  placeholder art per the platform roadmap in Section 0 — polish and the
  2.5D look are explicitly out of scope for v1; legibility of the judgment
  is what matters here.
- **Post-round screen:** after 3 misses (or after a fixed number of
  successful measures if you want a "win" condition too), show:
  - A scatter/list of timing offsets per swing (ms early/late) — show
    **raw uncorrected offsets** here (per the 4a design note), with the
    calibrated offset drawn as a reference line, so habitual bias stays
    visible even though scoring corrects for it.
  - A scatter/list or simple trend of sharpness per swing.
  - The logged beat-2/wind-up ictus timestamps as an inter-beat-interval
    consistency stat (variance of interval length across the round) — purely
    observational in v1, not scored, but worth surfacing since it's already
    being captured.
  - A **Settings** button leading to **Calibrate** (Section 4a) and, later,
    other options — keep this menu structure simple but present, since
    calibration access depends on it existing.
  - The per-swing data doubles as the session data referenced in the
    project's mid-term feedback-loop goal — keep the raw per-swing data
    structure simple (list of dicts or a small dataclass) so it's trivial to
    dump to CSV/JSON later without changing this phase's code.

**Reusability note:** because the detector/scorer/tier-table are kept
separate from presentation, this same core (state machine + tier lookup) is
meant to be the shared skeleton for other minigames in the larger set (e.g.
Strike It Rich, Take a Stab, Rhythm and Bruise) — those would swap the visual
theme and the tier-table's labels, not the detection or scoring logic. Keep
that separation clean even though only All-Star Swingers is being built now.

Deliverable: `game.py` (main loop, wires together metronome, detector,
calibration, scoring, and pygame rendering), `settings_menu.py` (post-round
menu + calibration entry point), `calibration.json` (runtime-generated,
not checked in), and a `session_log.py` helper that just holds/exports
per-swing data — keep this decoupled from rendering.

## 5. Phase 4 — Manual Playtest & Threshold Tuning Pass

Not new features — a dedicated pass to tune the constants introduced in
Phases 2–4 (rise-rate threshold, peak minimum, drop fraction, timing tier
windows, sharpness normalization range) against actual human swings, since
these cannot be correctly guessed from first principles. Budget real time for
this; it's expected that thresholds from Phase 2's offline validation will
need adjustment once calibration and live play are in the loop together.

**Exit criterion for the whole v1 build:** a first-time player can be handed
the right Joy-Con with zero explanation beyond "swing when you hear the
click," play a full round to 3 outs using the default (or previously saved)
calibration, optionally visit Settings → Calibrate afterward, and get a
summary that a non-technical observer (e.g. a music teacher) could look at
and say "yes, that reflects how consistent/clean their swings were."

## 6. Explicitly Deferred (not in scope for v1 — do not build yet)

- Per-axis / dominant-axis calibration instead of raw combined magnitude.
- Beat 2 (up-stroke/rebound) detection or scoring.
- Real song/audio-driven tempo instead of fixed-BPM metronome.
- **Audio following the conductor** (tempo dynamically tracking the
  player's pace) instead of the conductor following a fixed click — this is
  the eventual direction noted in Section 0, but not built now. Keep the
  Phase 1 beat-schedule/metronome logic modular enough that swapping the
  beat source later doesn't require rewriting the detector or scorer.
- Tempo ramps (accelerando/ritardando), time signature changes, syncopation.
- Dual Joy-Con (independent left/right hand tracking) — left Joy-Con support
  is deferred; v1 is right-hand only.
- Unity 2.5D port and VR port (see platform roadmap, Section 0) — both are
  real, planned stages, just not this document.
- Difficulty-adaptive systems, expandable song/minigame library beyond
  All-Star Swingers.
- Forcing calibration every session — v1 intentionally makes this optional
  and Settings-accessed per Section 4a; don't regress this into a
  mandatory pre-round step.

If any of the above turns out to be blocking v1 (e.g. raw magnitude proves
too noisy without dominant-axis isolation), stop and flag it rather than
quietly expanding scope — that's a design decision, not an implementation
detail.
